# MonoMelt v2: Phase 1 (Database & Schema Preparation)

## 1. Phase Overview

Phase 1 of the MonoMelt v2 Report Agent integration focuses exclusively on the persistence layer. Before any Python AI agents can aggregate data, or any Node.js workers can trigger exports to Notion, the underlying PostgreSQL database (managed via Supabase) must be strictly defined, secured, and optimized.

The goal of this phase is to design and implement the `project_reports` schema. This table will act as the single source of truth for the entire MonoMelt reporting lifecycle, ensuring that multi-agent outputs are safely versioned, efficiently queried by the React dashboard, and securely isolated per tenant.

This document serves as the comprehensive, 150+ line technical specification for executing Phase 1.

---

## 2. Architectural Objectives

### 2.1 State Management & Idempotency
Because the AI Decomposition pipeline can be run multiple times by a user (e.g., tweaking parameters to get a different strategy), the reporting layer must be **idempotent and version-controlled**. We cannot simply overwrite the `payload` column in a 1-to-1 project relationship. 

Instead, the `project_reports` table operates as an append-only ledger. Each time the `generate-report` job is executed, a new row is created with an incremented `version_number`. This provides users with a historical audit trail of their architectural transitions.

### 2.2 Security Isolation (Multi-Tenancy)
MonoMelt operates in a multi-tenant environment. It is mathematically critical that User A can never query or intercept the architectural blueprint reports belonging to User B. This isolation is enforced at the database level using PostgreSQL Row Level Security (RLS), bound strictly to the JWT `sub` (user_id) claim.

### 2.3 JSONB Optimization
The aggregated report generated by the Python FastApi service is a deeply nested JSON object. Storing this as standard `TEXT` is highly inefficient. The payload must be stored as the PostgreSQL `JSONB` binary format, allowing the API Gateway to perform structural queries (e.g., filtering for reports where `payload->>'overall_risk_score' = 'HIGH'`) without needing to load the entire document into memory.

## 3. Database Schema Specifications

### 3.1 Custom Enumeration Types
Before defining the tables, we must define the state machine for the report lifecycle. We use a PostgreSQL `ENUM` to guarantee data integrity and prevent string-typo bugs in the API Gateway.

```sql
-- Define the state machine for report generation
CREATE TYPE report_status AS ENUM (
    'pending',      -- Job is queued in BullMQ but Python has not started
    'generating',   -- Python FastAPI is actively querying Neo4j/LLMs
    'completed',    -- JSON is finalized and ready for Dashboard/Notion export
    'failed'        -- An error occurred during aggregation or generation
);
```

### 3.2 The `project_reports` Table Definition
This is the core table structure that must be executed in the Supabase SQL Editor.

```sql
CREATE TABLE IF NOT EXISTS public.project_reports (
    -- Primary Identity
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    
    -- Foreign Key Relations
    project_id UUID NOT NULL REFERENCES public.projects(id) ON DELETE CASCADE,
    owner_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
    
    -- Version Control
    version_number INTEGER NOT NULL DEFAULT 1,
    
    -- State Management
    status report_status NOT NULL DEFAULT 'pending',
    
    -- Core Data
    payload JSONB DEFAULT '{}'::jsonb,
    
    -- External Integrations
    notion_url TEXT DEFAULT NULL,
    
    -- Audit Timestamps
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
    
    -- Idempotency Constraint
    -- Ensures we never have two "v1" reports for the same project
    CONSTRAINT unique_project_version UNIQUE(project_id, version_number)
);
```

### 3.3 Indexing Strategy
To ensure the React Dashboard loads instantly, even when scanning thousands of historical reports across the platform, we must apply B-Tree indexes on the foreign keys and lookup columns.

```sql
-- Optimize looking up all reports for a specific project
CREATE INDEX idx_project_reports_project_id ON public.project_reports(project_id);

-- Optimize checking the status of reports (useful for the BullMQ worker polling)
CREATE INDEX idx_project_reports_status ON public.project_reports(status);

-- Optional: GIN index if we need to search inside the JSONB payload in the future
CREATE INDEX idx_project_reports_payload ON public.project_reports USING GIN (payload);
```

## 4. Row Level Security (RLS) Implementation

Security is not optional. The following RLS policies must be applied immediately after the table is created.

### 4.1 Enabling RLS
```sql
-- Turn on the RLS engine for this specific table
ALTER TABLE public.project_reports ENABLE ROW LEVEL SECURITY;
```

### 4.2 Read Policy (SELECT)
Users should only be able to view reports where they are the explicit `owner_id`.

```sql
CREATE POLICY "Users can view their own project reports"
ON public.project_reports
FOR SELECT
USING (auth.uid() = owner_id);
```

### 4.3 Delete Policy (DELETE)
Users should be able to delete their own historical reports to clean up their workspace.

```sql
CREATE POLICY "Users can delete their own project reports"
ON public.project_reports
FOR DELETE
USING (auth.uid() = owner_id);
```

### 4.4 Insert/Update Policy (Service Role Exception)
*Critical Architecture Note:* 
Because the reports are generated by the backend Python worker asynchronously (which does not possess the User's JWT token), standard `INSERT` and `UPDATE` policies tied to `auth.uid()` will fail with a 401 Unauthorized error. 

Therefore, we do **not** define an INSERT or UPDATE policy for authenticated web users. The frontend React application should *never* write directly to this table. 

Instead, the Node.js API Gateway and Python AI Service will instantiate their Supabase clients using the **`SUPABASE_SERVICE_ROLE_KEY`**. This master key bypasses all RLS policies, allowing the backend workers to safely insert and update the reports. The `owner_id` will be passed down from the API Gateway during the initial job enqueue phase.

## 5. Execution & Rollback Plan

### 5.1 Deployment Steps
1. Navigate to the Supabase Dashboard -> SQL Editor.
2. Paste the `report_status` ENUM definition and execute.
3. Paste the `CREATE TABLE` script and execute.
4. Paste the `CREATE INDEX` scripts and execute.
5. Paste the RLS enablement and Policy definitions and execute.

### 5.2 Rollback / Teardown
If the schema needs to be radically altered during development, a clean teardown script must be used to drop the constraints and types cleanly.

```sql
-- Teardown script for Phase 1 rollback
DROP TABLE IF EXISTS public.project_reports CASCADE;
DROP TYPE IF EXISTS report_status CASCADE;
```

---

## 6. Integration Hand-Off (To Phase 2)

Once Phase 1 is complete, the database is fully prepared to accept payloads. 

The Python backend (Phase 2) will query this schema as follows:
1. When triggered, Python queries: `SELECT MAX(version_number) FROM project_reports WHERE project_id = '...'`
2. Python calculates the new version: `new_version = max_version + 1`
3. Python constructs the JSON structure.
4. Python executes an upsert using the Service Role Key, setting `status = 'completed'` and dropping the JSON into the `payload` column.

This concludes the strict technical requirements for Phase 1 Database & Schema Preparation.
