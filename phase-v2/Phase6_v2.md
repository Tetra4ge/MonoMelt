# MonoMelt v2: Phase 6 (Notion MCP Integration)

## 1. Phase Overview

Phase 6 is the final architectural step of the MonoMelt v2 implementation. It connects the internal, enclosed ecosystem of MonoMelt to external, enterprise productivity tooling. Specifically, this phase implements the "Export to Notion" functionality utilizing the **Model Context Protocol (MCP)**.

While standard Notion API integrations require tedious, fragile mapping of JSON to deeply nested Block objects and complex OAuth flows, the MCP abstracts this complexity. By utilizing an officially supported (or community-built) Notion MCP Server, the MonoMelt Node.js API Gateway simply needs to send a structured payload to the MCP connector, which handles the heavy lifting of writing to the target workspace.

This document serves as the comprehensive, 150+ line technical specification for executing Phase 6.

---

## 2. Architectural Objectives

### 2.1 The MCP Translation Layer
The raw JSON payload generated by Phase 2 (Python AI Service) is structured for React components, not for Notion documents. Phase 6 must introduce a translation utility (`notion.util.js`) within the API Gateway. This utility will map keys like `executive_summary.business_impact` into Notion-compatible "Paragraph" blocks, and arrays like `cost_analysis.breakdown` into "Table" blocks.

### 2.2 Deep Linking Strategy
As decided during the architectural planning phase, Notion is incapable of natively rendering interactive D3.js or Neo4j graphs. Attempting to generate a static `.png` canvas export is computationally expensive and prone to failure. Instead, the Notion export will intentionally omit the visual graph and insert a hyperlinked "Callout Block" directing the enterprise user back to the MonoMelt dashboard (`/analysis/:projectId`) for interactive visualization.

### 2.3 Resilient Network Execution
Network calls to external APIs (even via MCP) are inherently unstable. The export route must implement exponential backoff for `429 Too Many Requests` responses and ensure that a failed export does not crash the Express server.

## 3. Implementation Specifications

### 3.1 The Translation Utility (`api-gateway/utils/notion.util.js`)
This file is responsible for converting the Phase 2 JSON schema into the structure expected by the Notion MCP.

```javascript
/**
 * Translates the MonoMelt JSON Report into Notion MCP Block structures.
 */
export const buildNotionPayload = (reportData) => {
    const blocks = [];

    // 1. Title & Executive Summary
    blocks.push({
        type: "heading_1",
        text: "Monolith Transformation Report"
    });
    
    blocks.push({
        type: "paragraph",
        text: reportData.executive_summary.business_impact
    });

    // 2. High-Level Metrics (Callout Block)
    blocks.push({
        type: "callout",
        text: `Total Services Extracted: ${reportData.executive_summary.total_services_extracted} | Overall Risk: ${reportData.executive_summary.overall_risk_score}`,
        icon: "📊"
    });

    // 3. Decomposition Strategy (List Blocks)
    blocks.push({
        type: "heading_2",
        text: "Proposed Microservices"
    });

    reportData.decomposition_strategy.forEach(service => {
        blocks.push({
            type: "bulleted_list_item",
            text: `**${service.service_name}** (Team Size: ${service.team_allocation})\nRationale: ${service.rationale}\nDependencies: ${service.dependencies.join(', ')}`
        });
    });

    // 4. Financial Projections (Table Block)
    if (reportData.cost_analysis) {
        blocks.push({
            type: "heading_2",
            text: "Financial Projections (Monthly)"
        });
        // MCP Table abstraction simplifies Notion's complex table API
        blocks.push({
            type: "table",
            headers: ["Metric", "Amount ($)"],
            rows: [
                ["Current Monolith", reportData.cost_analysis.current_monolith_cost_monthly],
                ["Target Microservices", reportData.cost_analysis.projected_microservices_cost_monthly],
                ["Infra Multiplier", `${reportData.cost_analysis.infrastructure_multiplier}x`]
            ]
        });
    }

    // 5. Deep Link to Interactive Graph
    blocks.push({
        type: "callout",
        text: `View the interactive Neo4j dependency graph here: https://monomelt.app/projects/${reportData.project_id}/analysis`,
        icon: "🔗"
    });

    return {
        title: `MonoMelt Report: ${reportData.project_id}`,
        blocks: blocks
    };
};
```

### 3.2 The API Route (`api-gateway/controllers/reports.controller.js`)
This is the route triggered by the Phase 5 React Dashboard when the user clicks "Export to Notion".

```javascript
import { supabase } from '../config/supabase.js';
import { buildNotionPayload } from '../utils/notion.util.js';
import axios from 'axios';

// Assuming the MCP server is running locally or accessible via internal network
const MCP_SERVER_URL = process.env.MCP_NOTION_SERVER_URL || 'http://localhost:3001/mcp/notion';

export const exportReportToNotion = async (req, res) => {
    try {
        const { projectId } = req.params;
        const userId = req.user.id;

        // 1. Fetch the latest JSON payload from Supabase
        const { data: report, error } = await supabase
            .from('project_reports')
            .select('*')
            .eq('project_id', projectId)
            .eq('owner_id', userId)
            .order('version_number', { ascending: false })
            .limit(1)
            .single();

        if (error || !report) {
            return res.status(404).json({ success: false, message: 'Report not found for export.' });
        }

        // 2. Check if it has already been exported
        if (report.notion_url) {
            return res.status(200).json({ 
                success: true, 
                message: 'Already exported.', 
                notion_url: report.notion_url 
            });
        }

        // 3. Translate JSON to MCP Blocks
        const mcpPayload = buildNotionPayload(report.payload);

        // 4. Send to Notion MCP Server
        // We use axios here; in a production app, wrap this in a retry utility (e.g., async-retry)
        console.log(`[API Gateway] Dispatching payload to Notion MCP...`);
        const mcpResponse = await axios.post(`${MCP_SERVER_URL}/pages`, {
            database_id: process.env.NOTION_DATABASE_ID,
            ...mcpPayload
        });

        const newNotionUrl = mcpResponse.data.page_url;

        // 5. Update Supabase with the generated URL
        await supabase
            .from('project_reports')
            .update({ notion_url: newNotionUrl })
            .eq('id', report.id);

        return res.status(200).json({
            success: true,
            notion_url: newNotionUrl
        });

    } catch (err) {
        console.error('[API Gateway] Notion Export Failed:', err.message);
        return res.status(500).json({ 
            success: false, 
            message: 'Failed to communicate with Notion MCP.' 
        });
    }
};
```

## 5. Error Handling & Idempotency

### 5.1 Prevent Duplicate Exports
As seen in Step 2 of the `exportReportToNotion` controller, the route is strictly idempotent. If a user clicks the "Export" button multiple times, the backend checks the `notion_url` column in Supabase. If the column is not null, it immediately returns a 200 OK with the existing URL, preventing duplicate pages from flooding the Notion workspace.

### 5.2 Graceful Degradation of MCP
If the MCP server is offline, the React frontend must not crash. The 500 error returned by the Express route will be caught by the React `try/catch` block, allowing the dashboard to display a standard "Toast" notification (e.g., "Failed to connect to enterprise workspace. Please try again later."), while keeping the internal MonoMelt dashboard fully operational.
